## 问题出在哪：你的 Qwen-Turbo Node.js 代码为什么烧钱？

大多数 “跑一次亏一次” 的 Node.js 示例，通常有以下几个致命伤：

**1. 频繁建立连接且不重用**
很多教程的代码，每次请求 API 都重新创建一个 HTTP 客户端对象。这在 Node.js 里是性能大忌，因为 TCP 握手和 TLS 协商的开销会浪费大量时间和网络资源。如果你调用 Qwen-Turbo 只是为了发一条简单指令，那每次请求的“建立连接”成本，可能比生成回复本身的 Token 费用还高。

**2. 错误的请求体设计导致过量输出**
Qwen-Turbo 支持参数调节，但很多旧代码完全忽略了 `max_tokens` 和 `temperature` 的精细控制。比如你问个“今天天气怎么样？”，AI 给你写了一篇 500 字的详细分析。这 500 字的 Token 费用，就是无谓的浪费。

**3. 缺少智能的重试与超时机制**
网络抖动时，旧代码可能直接抛错或无限重试。如果重试没带指数退避，服务器一波动，你就会瞬间触发好几次重复请求。尤其是没有设置超时时间时，一个请求卡住不动，你以为它失败了，又在本地重跑一次，结果几秒后收到三四个完整的回复。

## 进阶优化：让你的 Node.js 代码“一次请求，终身省钱”

有了不亏钱的代码，我们可以更进一步，做一些优化让成本更低。

**1. 复用 HTTP 连接（Keep-Alive）**
`openai` 这个 npm 库默认是启用了 HTTP/1.1 的 keep-alive 的，这意味着它会在单个 TCP 连接上发送多个请求。上面的代码示例中，`client` 对象被实例化一次后，后续的所有 `callQwenTurbo` 调用都会复用同一个底层连接，彻底避免了文章开头说的“连接浪费”。

**2. 精确控制输出**
我们代码里的 `max_tokens: 512` 是一个很好的数字。对于绝大多数日常问题（代码解释、文案生成、问答），512 个 Token 是绝对足够的。如果你只想要关键词，把它改成 50 甚至 20。这样即使 API 返回内容超长，你也不会被收费。

**3. 利用流式输出减少等待**
如果用户需要的是即时反馈（比如打字机效果），你可以把代码改成流式（stream）模式。虽然这本质上并没有减少 Token 消耗，但它能让你在收到完整回复之前就停止输出（比如用户点了“停止”按钮），从而避免无效生成。

javascript
const stream = await client.chat.completions.create({
  model: 'qwen-turbo-latest',
  messages: [{ role: 'user', content: prompt }],
  max_tokens: 512,
  stream: true,
});
for await (const chunk of stream) {
  process.stdout.write(chunk.choices[0]?.delta?.content || '');
}


流式输出对 Node.js 特别友好，因为它基于 async iterator，非常适合处理大模型的实时数据流。
