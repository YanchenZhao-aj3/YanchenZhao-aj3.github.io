## 陷阱一：你以为你只调了1次，计费却算你2次

这是最常见的“小白坑”。不少兄弟在调试代码时，喜欢发送一次请求，然后“看看返回”，如果返回报错了，就再发一次。这本身没问题，但你得搞清楚 Kimi API 的计费规则是“按你发送的请求 Token 总量”算，而不是“按成功返回的响应 Token”算。

**真实案例：** 有个做智能客服的哥们，为了测试 Kimi 能不能正确识别用户情绪，写了段脚本，每遇到一次超时或者网络波动，程序就自动重试。结果月底账单出来后，他傻眼了：Token 消耗量比预期高了一倍多，仔细一查，全是重试请求产生的费用。更坑的是，Kimi 的某些模型在输入 Token 计数上本身就比一些竞品更“慷慨”一点。

![Image placeholder: 一张展现多次重试导致Token消耗骤增的图示]

**避坑方法是：**
- **务必在你的代码中实现健壮的重试机制，并加上指数退避（Exponential Backoff）。** 第一次请求报错，等 1 秒再试；第二次等 2 秒；第三次等 4 秒……别给你应用喂 Token。
- **仔细检查你的日志。** 调一个 Kimi API 接口，日志里如果出现多条相同请求记录，大概率就是出问题了。
- **利用本地缓存。** 如果某些查询结果是固定的（比如常见问题），直接在本地缓存，不要每次都去调 Kimi 的 API。

## 陷阱二：免费的“上下文缓存”？别信，钱都扣在你看不到的地方

Kimi 的一大优势是“超长上下文”，1M 甚至更长。很多开发者觉得，既然上下文这么长，那我是不是可以把整个对话历史、甚至整篇技术文档都塞进去当上下文？然后利用它的“上下文缓存”（Context Caching）功能，想着“这块数据是缓存好的，不会重复收费”。

**大错特错！** 这是我最常帮人排查的隐藏收费陷阱之一。

许多 API 提供商（包括某些 Kimi 的代理服务）的“上下文缓存”是有**黑洞**的。你以为系统帮你缓存了整个上下文，但实际上，每次请求时，系统还是会重新计算你输入的那部分 Token。更坑的是，有些服务商为了计费方便，会把你的每次输入都视为“新 Token”，然后按全价收费。你的“缓存”只是系统层面帮你加速了一下响应，但计费系统根本不管你这套。

**避坑方法很粗暴：**
- **确认你使用的 API 中转平台是否支持真正的“缓存命中不计费”。** 问清楚计费逻辑，不要想当然。
- **严格控制上下文长度。** 每次请求，只带真正必要的、最新的对话记录，别把你和 Kimi 一个月的聊天记录全塞进去。
