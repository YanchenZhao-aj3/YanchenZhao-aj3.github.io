核心问题在于，很多中转站对GLM系列模型的接口路径和模型名称，有特定的映射规则。你照着OpenAI的格式敲，它根本找不到对应的路由。

## 坑二：贪便宜用“限时特价”却意外触发高费率模型，Token像坐火箭

**根因分析：“限时特价”是诱饵，但自动补全是陷阱！**

**最优解法：**

永远不要依赖默认配置，要强制指定分组和模型。

**正确代码模板（包含分组指定）：**

.then((response) => {
  console.log(JSON.stringify(response.data));

## 坑三：流式输出不完整或中断，导致“假死”式浪费

**真实案例：**

我写了一个Node.js流式输出（SSE）的程序，用来显示AI打字机的效果。结果在调用GLM时，经常跑到一半就卡住了，既不报错，也不输出新内容。我以为代码有问题，反复调试，白白消耗了Token。

**根因分析：**

很多API平台对流式的处理并不稳定。尤其当网络波动，或者服务端繁忙时，流式连接可能被中断，但客户端并未收到正确的断开信号，导致程序在傻等，而API后台仍然在计费。

**最优解法：**

必须实现健壮的流式处理逻辑，包括超时重试、自动断开和断点续传。

**最优代码模板（带流式控制和超时处理）：**

javascript
const axios = require('axios'); // 需要axios ^1.0.0
const EventSource = require('eventsource');

const API_KEY = '你的云雾API Key';
const BASE_URL = 'https://www.yunwuai.cc/v1';

const body = {
  // 使用GLM模型
  model: "glm-4",
  messages: [
    {
      role: "user",
      content: "你好，请用一首诗来介绍你自己。"
    }
  ],
  stream: true // 启用流式输出
};

const url = `${BASE_URL}/chat/completions`;

const source = new EventSource(url, {
  headers: {
    'Authorization': `Bearer ${API_KEY}`,
    'Content-Type': 'application/json'
  },
  method: 'POST',
  body: JSON.stringify(body)
});

// 设置超时，15秒内没有收到任何数据，视为超时
let timeoutId = null;
const resetTimeout = () => {
  clearTimeout(timeoutId);
  timeoutId = setTimeout(() => {
    console.warn('[警告] 流式响应超时，主动断开连接');
    source.close();
    // 这里可以添加重试逻辑
    // 重新调用上面的fetch请求
  }, 15000); // 15秒超时
}

source.onopen = (event) => {
  console.log('连接已建立');
  resetTimeout();
};

// 关键监听 data 事件
source.onmessage = (event) => {
  resetTimeout(); // 收到数据就重置超时
  if (event.data === '[DONE]') {
    console.log('流式输出完成');
    source.close();
    return;
  }
  try {
    const parsed = JSON.parse(event.data);
    const content = parsed.choices[0].delta.content || '';
    process.stdout.write(content); // 模拟打字机效果
  } catch (error) {
    console.error('解析错误:', error);
  }
};

source.onerror = (error) => {
  console.error('流式连接发生错误:', error);
  source.close();
  clearTimeout(timeoutId);
};


**核心经验：** 用流式的时候，千万别裸奔。加上超时机制和重试逻辑，是避免“假死式”浪费Token的唯一良药。
